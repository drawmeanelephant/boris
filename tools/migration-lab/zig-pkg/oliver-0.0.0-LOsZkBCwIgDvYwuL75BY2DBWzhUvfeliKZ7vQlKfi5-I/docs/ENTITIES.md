# Markdown entity and numeric character references

**Status: implemented** — CommonMark 0.31.2 §2.5, scorecard 17/17.

This document is the contract for Oliver's §2.5 entity handling: named
references against the authoritative WHATWG HTML5 entity list, decimal and
hexadecimal numeric references, and the places they are recognized. It is
derived from the CommonMark 0.31.2 spec prose and examples plus the data
source the spec itself names.

Clean-room note: the entity table is generated from
<https://html.spec.whatwg.org/entities.json> — an HTML-*specification* data
source, explicitly cited as authoritative by §2.5 ("The document
<https://html.spec.whatwg.org/entities.json> is used as an authoritative
source for the valid entity references"). No parser implementation source
was consulted for the decoding rules; the recognition points come from the
spec prose.

## 1. What the spec says

- **Named references:** `&` + a valid HTML5 entity name + `;`. The WHATWG
  entities.json list is authoritative. §2.5 requires the trailing `;` —
  the legacy HTML no-semicolon forms are *not* valid CommonMark references.
- **Decimal references:** `&#` + 1–7 arabic digits + `;`.
- **Hexadecimal references:** `&#` + `X`/`x` + 1–6 hex digits + `;`.
- **Range rules:** an invalid Unicode code point becomes U+FFFD (REPLACEMENT
  CHARACTER); U+0000 also becomes U+FFFD (security). Surrogates are invalid
  and become U+FFFD.
- **Recognition points:** "Entity and character references are recognized
  in any context besides code spans and code blocks, including URLs, link
  titles, and fenced code block info strings" — and are *not* recognized
  in code blocks and code spans.
- **Not structural:** references cannot stand in place of characters that
  define structure — `&#42;` is text, never an emphasis delimiter, bullet
  marker, or thematic-break byte (spec example 37: `&#42;foo&#42;` renders
  literal `*foo*`).
- **Conformance:** a conforming parser "need not store information about
  whether a particular character was represented in the source using a
  Unicode character or an entity reference" — the decoded character is the
  character, so it is escaped like any other text byte at render time
  (`&lt;` → `&lt;` in output, `&#34;` → `&quot;`, `&ouml;` → `ö`).

## 2. The table and the generator

`src/entities.zig` embeds the full semicolon-terminated WHATWG entity list
(2,125 names — entities.json's ~2,231 entries minus the no-semicolon legacy
forms), sorted by name for binary search, each with one or two code points
(`b == 0` for single-codepoint entities). It is generated by
`tools/gen-entities.py` from a local copy of entities.json:

```
curl --fail --location https://html.spec.whatwg.org/entities.json -o /tmp/entities.json
python3 tools/gen-entities.py --entities /tmp/entities.json
zig fmt src/entities.zig
```

This mirrors the established `src/unicode.zig` + `tools/gen-unicode.py`
pattern (generated standard data, checked in, never hand-edited). The
generator also emits the `decodeAt` lookup and its unit tests, so the
decoder and the table are regenerated together.

`entities.decodeAt(src, amp)` requires `src[amp] == '&'`, tries a named
reference (binary search, bounded name scan) and then the numeric forms
(`&#digits;` / `&#xX hex;` / `&#X hex;`), applies the §2.5 range rules, and
returns `{ bytes, len, next }` where `next` is the index just past the `;`.
Unknown names, missing `;`, overlong digit runs, and out-of-range code
points yield `null` — the `&` stays literal.

## 3. Where decoding happens

Oliver decodes at **emit/render time**, never in the parser, so:

- the delimiter scanner, link discovery, and block recognizers stay strictly
  byte-based (`&#42;` can never act as a delimiter — spec example 37);
- text nodes keep borrowing the source (DOCUMENT-MODEL invariant 9);
- the decoded character is escaped like any other text byte.

The recognition points, all sharing one decode walk:

| context | mechanism | notes |
| --- | --- | --- |
| paragraph / heading text | `html.writeEscapedText` | decode then escape; `&lt;` → `&lt;`, `&ouml;` → `ö` |
| code spans, code blocks | `html.writeEscaped` (unchanged) | references stay literal |
| link/image destinations + titles | `resolveEscapes` → `resolveEntities` (arena-owned) | then §2.4 backslash escapes; percent-encoding is the renderer's href policy |
| fenced info strings | `resolveEscapes` | first word becomes the `language-…` class |
| image alt flattening | `flattenAlt` | decoded content flattens like text |
| autolinks | `resolveEntities` on the content | decoded in both href and label (see §4.4) |

Backslash-escaped `&` (`\&ouml;`) is never decoded: the escape splits the
text node (src/markdown.zig `emitText` — an escaped first byte never merges
with following text), so the renderer sees the escaped character as a
separate node and decodes nothing (spec example 14).

The inline and block passes never see decoded bytes, which is what makes
the "not structural" rule automatic. Entity references inside an HTML tag
are tag bytes (raw HTML is consumed wholesale; §6.6) and stay verbatim —
the tag is never decoded.

## 4. Chosen behaviors and recorded divergences

1. **The WHATWG entities.json list is the name source** (the spec names
   it), with the no-semicolon legacy forms excluded because §2.5 requires
   the trailing `;`. `&copy` without `;` stays literal.
2. **Decoded whitespace is emitted literally.** A decoded tab
   (`&#9;`), CR, or LF is written as that byte, matching the reference
   output (spec example 42's `→` represents a literal tab after the
   harness's `→`→tab normalization). The escaper does not touch
   whitespace.
3. **Numeric range rules:** invalid code points and surrogates → U+FFFD;
   U+0000 → U+FFFD (not the text writer's ordinary NUL handling, which
   also yields U+FFFD — same output, per the spec's security rule).
4. **Autolinks decode references** in both the href and the label: §2.5
   recognizes references anywhere except code spans/blocks and HTML tags,
   and an autolink is none of those. This matches the reference
   implementation (`cmark_clean_autolink`/`make_str_with_entities`). The
   decoded `&` then percent-encodes to `%26` in the href and re-escapes
   to `&amp;` in the label (docs/AUTOLINKS.md §4.4). No spec example pins
   this; it is recorded as a chosen behavior.
5. **`resolveEntities` borrows when there is nothing to decode** — the
   common no-reference case allocates nothing; only spans containing a
   valid reference allocate an arena copy.

## 5. Verification and test plan

1. §2.5 spec examples 25–41 byte-for-byte via the spec-conformance
   harness: **17/17**. One section example (#31, `<a href="&ouml;&ouml;.html">`)
   is a type-7 HTML block — a complete tag on its own line stays raw and
   undecoded (docs/HTML-BLOCKS.md), which is why the §4.6 HTML-block slice
   shipped with this milestone.
2. Fixtures: `entity-text` (decoded + escaped output), `entity-nonentity`
   (missing `;`, unknown names, `\&`), `entity-code` (literal in code
   spans/blocks), `entity-structural` (`&#42;` not a delimiter/marker),
   `entity-info` (fenced info string), plus the updated `escape-special`
   and `link-entity` pairs.
3. Unit tests in `src/entities.zig` (generated): corpus forms, numeric
   ranges, surrogates, `next` accounting; plus markdown tests for the
   escape-split (`\&ouml;` stays undecoded) and the no-merge rule.
4. Quality gate: `zig fmt --check`, `zig build`, `zig build test`, and the
   classified conformance gate green (652 supported / 0 not-yet / 0
   divergences — full conformance — after the HTML-blocks-types-1–5 and
   full-conformance milestones).

## 6. Completion

The §2.5 slice landed with the HTML-block slice (docs/HTML-BLOCKS.md):
652/652 total, 0 regressions, and the §4.6 HTML-block family is complete
(44/44) — the HTML blocks themselves never decode entities, since their
content is verbatim, which is why the entity spec section stayed green
while the block family grew. Entities themselves are complete: 17/17.
